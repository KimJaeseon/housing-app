이 문서는 **목표 기능과 현재 구현 상태를 구분한 개발 기준 문서**다. ‘구현’은 운영 서비스 완성이나 모든 실제 자료의 검증 완료를 뜻하지 않는다. 외부 승인, 실데이터 확인, 모바일 실기 검사는 별도로 표시한다. 기존 요구사항의 범위를 확대하거나 변경하지 않는다.

## 1. 목적 및 사용자

사용자가 수도권 지역을 입력하면 공식 공공주택 공고를 조사하고, 신청 일정·주택형·금액·자격·원문 근거를 확인할 수 있도록 한다. 확인이 끝난 정보와 추가 확인이 필요한 정보를 분리하여 잘못된 신청 판단을 줄인다. 화면 읽기 사용자가 지도나 시각적 도움 없이 주요 과업을 완료할 수 있어야 한다.

| 사용자 | 이용 범위 |
|---|---|
| 비로그인 사용자 | 지역 검색, 목록·상세·공식 원문 확인. 향후 임시 맞춤 조건 입력 |
| 로그인 사용자 (예정) | 비로그인 기능에 더해 관심 공고·맞춤 조건 저장 및 삭제 |
| 개발·운영 담당자 | API 키 등록, 조회 기간·서버 설정, 검사 실행, 장애 확인. 관리자 화면은 현재 없음 |

최초 출시 목표는 Android·iOS의 제한된 사용자 대상 시험 운영이다. 현재는 로컬 서버와 Expo 웹에서 연결 및 화면을 검증하고 있으며, 앱스토어 공개 배포 완료 상태가 아니다.

## 2. 범위와 현재 상태

### 2.1 목표 범위

- 서울·인천은 광역시 전체, 경기는 시·군 단위로 조회한다. 동명 지역은 사용자에게 구분을 요청한다.
- 공공 임대주택과 공공분양을 대상으로 한다. 민간 아파트 분양은 제외한다.
- 접수 예정·접수 중이면서 검증이 완료된 공고를 기본 목록에 표시한다.
- 주소·지역명을 텍스트로 제공한다. 지도, 자동 청약 신청, 당첨 예측, 알림 구독, 유료 결제는 이번 범위가 아니다.
- 맞춤 조건은 선택 사항이며 자격이나 당첨을 확정하지 않는다.

## 5. 처리 흐름

### 5.1 목록 조사

1. 사용자가 서울 검색을 실행하면 앱이 세션 식별 토큰과 새 요청 중복방지 키를 준비한다.
2. 서버가 지역·세션·처리 용량을 확인하고 검색 작업을 생성한다.
3. 서버가 암호화 파일에서 LH 키를 읽고 설정된 기간의 목록을 조회한다.
4. 요청 조건의 응답 반영, 페이지 중복·총건수·지역·유형·공식 URL을 확인한다.
5. 마감·취소 공고를 제외 목록에 배치하고 나머지는 확인 필요 상태로 제공한다.
6. 원문 검증이 연결되지 않은 현재 구현에서는 목록 수집 성공도 조사 일부 완료(partial)로 종료한다. 현재 실제 수집 경로는 확인 완료 공고를 생성하지 않는다.
7. 앱은 작업 ID·revision을 대조하고 이전 검색의 늦은 결과를 무시한다.

### 5.2 공급정보 조회

1. 사용자가 상세에서 공급정보 조회를 누른다.
2. 서버는 부모 검색의 소유권과 해당 검색에 공고가 존재하는지 확인한다.
3. 목록에서 얻은 공고 식별자로 지원 레이아웃의 공급정보를 요청한다. 앱에서 임의 외부 URL·키를 전달하지 않는다.
4. 응답의 공고 식별자·성공 헤더·구조·수치·단위를 검증한다.
5. 주택형별 값, 근거 위치와 확인 시각을 별도의 공급 결과로 반환한다. 공고의 검증 상태나 마감 여부는 바꾸지 않는다.
6. 동일 검색·공고의 재요청은 저장된 결과를 재사용한다. 승인 반영 후에는 새 검색에서 다시 요청한다.
7. 화면 이탈 시 앱의 대기 요청을 중단한다. 이미 시작된 서버의 외부 요청은 종료될 수 있지만 이탈한 화면에 결과를 적용하지 않는다.

### 5.3 향후 검증 완료 판정

공급기관·공식 원문, 공공주택 유형, 공급 지역, 유효 모집 회차와 접수 일정, 정정·취소 관계, 모집 단위별 금액 조건 및 자격 근거가 모두 충족되어야 한다. 원문이 추후 확정을 명시한 경우 그 문장과 근거를 보존한다. 추출 실패를 추후 확정으로 바꾸지 않는다. 제목 유사성이나 게시일만으로 정정 관계를 확정하지 않는다.

## 6. 구성 및 프로그램 모듈

현재 구성은 `Expo 앱/웹 → FastAPI 로컬 서버 → LH 공식 API`다. 키 파일은 서버에서만 접근한다. 서버 작업과 공급 결과는 메모리에 보관하며 현재 데이터베이스는 없다. Supabase 인증·PostgreSQL은 향후 기본안이다.

| 모듈 | 위치 | 역할 |
|---|---|---|
| 앱 화면 | `frontend/App.tsx`, `LiveNotice.tsx` | 검색·목록·상세·공급정보·예시 화면, 초점 복귀 |
| 앱 API 처리 | `frontend/useSearchApi.ts` | 세션, 요청·폴링·취소, 응답 형식 및 오래된 결과 검사 |
| 지역 처리 | `frontend/search.ts` | 서울 입력 정규화 |
| 검색 API | `backend/app.py` | 작업 생성·상태·취소, 세션 소유권, 공급정보 생성/조회, 용량 제한 |
| 목록 수집 | `backend/lh_list.py`, `lh_response.py` | 페이지 수집, 공개 필드 정규화, 목록 분리 |
| 공급정보 | `backend/lh_supply.py` | 유형별 요청·응답 확인, 주택형 fact 및 근거 생성 |
| 공통 LH 처리 | `backend/lh_probe.py`, `lh_errors.py`, `lh_adapter.py` | 요청 규격·키 정규화·오류 코드·접속 점검 경로 |
| 계약 검증 | `backend/validation.py` | JSON Schema 및 의미 검증, 잘못된 결과 차단 |
| 키 및 실행 | `backend/key_store.py`, `serve_lh.py`, `save-lh-key.cmd` | DPAPI 저장·조회, 조회 기간 설정, 로컬 서버 시작 |

세션 토큰은 현재 앱에서 생성하는 작업 접근용 값이며 로그인 인증을 대체하는 계정 체계가 아니다. 서버는 해시로 소유자를 비교한다. 토큰 길이는 32~128자다. 요청 중복방지 키는 1~128자다. 허용하지 않은 검색 요청 필드는 거부한다.

공통 HTTP 오류: 토큰 누락·형식 불충족 401, 없는 작업·타 소유자·없는 공고 404, 요청 충돌·부모 검색 미종료 409, 미지원 지역·잘못된 요청 422, 처리 용량·워커 오류 503. LH 외부 실패는 대개 내부 API의 상태·error_code로 전달하므로 HTTP 응답 성공만으로 공고 조회 성공을 판단하지 않는다.

작업 상태 계약은 queued / researching / verifying / completed / partial / failed / cancelled다. 현재 실제 목록 경로는 queued → researching → partial 또는 failed이며 취소 가능하다. verifying/completed는 계약상 존재하지만 실제 원문 검증 성공 경로가 아직 연결되지 않았다.

공급정보는 researching → available / empty / failed다. available은 주택형 반환, empty는 정상 응답에 주택형 없음이다. empty는 공급 세대수 0이라는 뜻이 아니다. 모집 상태는 scheduled / open / closed / cancelled / unknown, 검증 상태는 verified / needs_review로 관리한다. 현재 서버는 verified 결과 생성을 허용하지 않는다.

## 10. 보안·보관·운영 제한

- 키는 `.secrets/lh-service-key.dpapi`에 Windows 현재 사용자 범위로 암호화 저장한다. 파일은 Git 및 수동 공유 대상에서 제외한다. 같은 계정 권한의 프로세스로부터 완전히 격리되는 방식은 아니다.
- 키 값·인증 쿼리 URL·원응답을 앱 배포 파일, 안내 문서, 일반 로그에 넣지 않는다. EXPO_PUBLIC_ 환경변수에 키를 설정하지 않는다.
- 서버만 키를 복호화하며, 키는 메모리와 공식 HTTPS 인증 요청에서 사용된다. LH_SERVICE_KEY가 별도로 설정되어 있으면 파일보다 우선하므로 운영 시 설정 충돌을 확인한다.
- 현재 서버는 단일 프로세스·로컬 실행용이다. 작업·중복방지 기록·공급 결과는 메모리이며 영구 저장·자동 만료·다중 프로세스 공유가 없다.
- 검색 작업은 최대 1,000개이며 만료 정리가 없어 도달하면 신규 생성이 거부된다. 시험 중 재시작 시 기존 작업이 사라지는 점을 안내한다. 운영 배포 전 보존 기간·정리 정책을 구현해야 한다.
- 기본 서버 주소는 127.0.0.1:8000이다. 허용 웹 origin은 localhost:8081, 127.0.0.1:8081, QA용 127.0.0.1:18800으로 제한되어 있다. 공개 배포는 별도 인증·HTTPS·호스팅·비밀 저장소·보존 정책 검토가 필요하다.
- 개인정보·증빙 업로드는 현재 요구하지 않는다. 향후 맞춤 조건은 최소 정보만 받고 저장 목적·삭제 경로를 제공한다.

## 15. 원문 항목 확인 구현 (1.1 / 2026-09-22)

### 현재 동작과 범위

- UI-03B: 상세에 **공고문 항목 확인** 버튼과 PDF 원문 열기, 항목별 페이지 근거를 추가했다.
- `backend/lh_document.py`는 목록에서 검증한 공식 상세 URL을 읽고 해당 페이지의 공고문 PDF 한 개를 식별한다. 보조 팸플릿은 공고문으로 사용하지 않는다. PDF가 없거나 복수이면 확정하지 않는다.
- 상세의 공고 ID·제목과 현재/원공고 식별자, 정정 사유를 확인한다. HTTPS 공식 호스트만 사용하고 리다이렉트는 따르지 않는다. 키는 이 공개 페이지/PDF 요청에 전송하지 않는다.
- `backend/document_reviews/2015122300020605.json`은 2026-09-17에 PDF 텍스트와 렌더링된 1·2·3·12쪽을 대조한 검토 기록이다. 표본 한 건의 검토된 항목이며 임의 PDF에서 자격·가격을 자동 추론하는 범용 추출기가 아니다.
- 매 새 검색의 원문 요청에서 PDF SHA-256, 현재/원공고 ID, 정정 사유가 모두 맞아야 기록된 항목을 반환한다. PDF 또는 관계가 달라지면 기존 값은 보류한다. 알려지지 않은 PDF는 검토 필요로 반환한다.
- 원문 API의 상태는 researching / partial / failed이고, `reviewed=true`는 반환된 항목의 검토 기록 일치만 뜻한다. 공고 전체 verified로 승격하지 않는다.
- 21A의 대학생·청년 무소득·청년 유소득 금액을 구분하고, 보증금 천원 단위를 원으로 환산했다. 최대 전환 금액은 기본 조건과 분리한다. 공급정보 API의 ‘공고문 참조’ 응답 자체를 수정하지 않는다.
- 접수 시각·발표 일정과 대상 개요를 제공하되 세부 소득·자산 가산, 우선배정 및 개별 자격 판정은 하지 않는다. PDF의 계약 ‘추후 개별통보’와 웹의 광범위한 계약기간이 다르므로 웹 기간을 확정 계약 일정으로 사용하지 않는다.

### 내부 API와 데이터

| 메서드·경로 | 동작 |
|---|---|
| POST `/v1/search-jobs/{id}/notices/{notice_id}/document` | 202, 원문 조회 시작 또는 동일 검색·공고 결과 재사용 |
| GET `/v1/search-jobs/{id}/notices/{notice_id}/document` | 200, 결과 조회. 미요청은 404 |

검색·공급정보와 같은 세션 소유권, 부모 작업 partial/completed 조건, 워커·슬롯 상한을 적용한다. `serve_lh`에서 LH_ENABLE_DOCUMENT=1을 설정한다. 일반 서버 실행에서는 기본 비활성이다.

`document_result`: job_id, notice_id, status, error_code, checked_at, source_url, pdf_url, sha256, filename, current_id, original_id, reviewed, facts, warnings. 각 fact는 category(address/schedule/rent/eligibility/correction), label, value, page로 구성한다. 읽기용 문장 데이터이며 맞춤 자격 판정에 직접 사용하지 않는다.

상세 HTML 1MiB, PDF 10MiB, 요청별 10초, 앱 총 대기 35초 제한. 다운로드 파일은 서버 작업에서 메모리로 비교하며 사용자 제공 경로나 임의 URL을 받지 않는다. 장기 보관용 표본과 검토 기록은 저장소 내 개발 증거로 별도 관리한다.

현재 확인 근거: [원문 연결 검증 기록](validation/2026-09-22_DOCUMENT_INTEGRATION.md), [실제 서버 응답](validation/2026-09-22_DOCUMENT_LIVE_RESPONSE.json). 기존 날짜의 검사 수치는 당시 결과로 보존한다.
