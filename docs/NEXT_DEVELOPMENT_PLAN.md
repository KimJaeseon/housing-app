**2026-10-08 자격 모델링 진행:** 강서염창 보존 PDF 8·9쪽의 기준일, 성년 원칙·미성년 예외 4가지, 주택소유 검증 대상 원칙·예외 3가지를 별도 근거 10개와 규칙 9개로 구조화했다. 전용 Schema·CLI는 대상과 예외 관계·근거·문서 해시 및 미검토 범위를 검사한다. 개인 평가와 앱/API 연결은 하지 않았다. 다음은 전체 세대 정의·주택소유 인정 예외·소득·자산·공급유형별 자격이다. ## 3. 완료한 P1 작업과 검증 경계

### 문제

P1 착수 전에는 검토 기록이 한 공고의 JSON이었고 독립 검사 도구가 없었다. 현재는 세 공고의 기록을 Schema·CLI·런타임에서 검사한다. 다만 현재 도구는 금액 환산과 원문 표의 의미를 자동 증명하지 않는다.

### 구현한 작업

1. **검토 기록 전용 Schema 정의:** 공고 식별자, 파일 해시, 전체 페이지 수, 검토 시점·방법, 원공고/현재공고 관계, 사실별 페이지와 최소 근거, 미검토 범위를 필수화한다.
2. **검사 CLI 작성:** 공식 PDF와 기록을 입력받아 해시, 필수 항목, 페이지 범위, 중복 식별자, 위치 표기의 쪽 번호를 검사한다. 단위·조건과 본문 값의 진위는 사람이 대조하며 P3에서 기계 검증을 확장한다. 파일을 읽는 도구이며 외부로 문서를 전송하지 않는다.
3. **추출 후보와 검토값 분리:** 텍스트/PDF 표 추출은 후보 단계로 보관한다. 렌더링 대조 전 값을 앱의 확인값으로 사용하지 않는다. 추출 실패·OCR 불확실성은 명시한다.
4. **기존 기록 이관:** 서울번동3 17항목을 새 형식으로 옮기고, 기존 화면·금액·단위·페이지 근거를 보존한다.
5. **검토 시점 표시:** 원문 재조회 시각과 항목 검토일을 구분해 응답과 화면에 표시한다.

구현 위치: `shared/contracts/` 검토 기록 Schema, `backend/document_reviews/`, `backend/document_review.py`, `lh_document.py`, `validation.py`, `useSearchApi.ts`, `LiveNotice.tsx`, 해당 테스트와 안내 문서.

### 수용 기준

- 정상 기록은 통과하고 공고 ID·해시·페이지 범위·근거가 잘못된 기록은 거부한다.
- 원격 PDF 바이트가 바뀌거나 정정 관계가 바뀌면 검토값을 보류한다.
- 보증금 천원→원 환산과 기본/최대 전환 조건, 소득 유무별 조건이 유지된다.
- 미검토 부분과 검토 날짜를 화면에서 구분할 수 있다.
- 문서 검토 기록 강화만으로 verified 생성 차단을 해제하지 않는다.

## 4. P2~P4에서 반드시 해결할 항목

다음 착수 순서는 (1) 자격 조건의 적용 대상·예외를 근거와 함께 모델링하고, (2) 인천 취소 이력과 새 공고 이력 사이의 명시적 근거 및 별도 변경 공지를 조사하며, (3) 미검토 주택형·소득구간을 확대하는 것이다. 두 이력의 직접 연결이 확인되기 전에는 취소 공고의 사실을 새 공고에 복사하지 않는다.

| 항목 | 현재 한계 | 구현·검사 방향 |
|---|---|---|
| 표본 범위 | 마감 정정공고 한 건·마감 비정정공고 한 건·조회 당시 접수 중 정정공고 한 건·PDF 없는 실제 취소 공고 한 건 | 취소의 원공고·재공고 번호 연결. 상태가 바뀔 수 있으므로 접수 중 표본의 조회 날짜와 PDF 일정 구분 |
| 첨부 선택 | 공고문 PDF 한 개만 허용 | 파일 역할과 버전 구분. 복수 PDF는 임의 선택하지 않고 사유 표시 |
| 접수 회차 | 읽기용 일정 문장 | 시작/종료·시간대·신청 대상·신청 단계 구조화. 미명시 시각을 채우지 않음 |
| 금액 | 설명 문자열과 API fact가 별도 | 원문 단위·환산값·대상·전환 조건·유효 시점 보존, 공통 모집 단위에 연결 |
| 자격 | 공급 대상 개요만 제공 | 무주택 대상 범위·소득/자산 기준·가산·예외를 근거와 연결. 개인 적격 단정 금지 |
| 정정 | 상세 메타정보와 등록 기록 대조 | 별도 수정 공지·취소·일정 변경 조사. 관계 미해결 시 승격 금지 |
| 검증 완료 | verified 전면 차단 | 필수 항목별 검증 결과와 누락 이유 모델을 먼저 정의한 후 실제 판정기 연결 |

P4 완료는 화면에 확인 완료 탭이 있다는 것으로 판단하지 않는다. 한 항목이라도 핵심 근거가 누락·상충하면 실패하는 부정 사례 검사가 필요하다. 한 출처의 실패가 다른 공고의 유효한 근거를 지우지 않도록 출처 상태와 공고 상태를 분리한다.

## 5. 사용자가 직접 할 수 있는 확인

- 서버 재시작 → 새 검색 → 정정공고 상세 → 공급정보 조회 → 공고문 항목 확인을 실행한다.
- PDF 2쪽에서 21A 소득 유무별 기본 금액과 최대 전환 금액을 비교한다. 12쪽에서 접수와 서류제출 단계를 구분한다.
- 현재 공고가 마감으로 제외되고, 확인 항목이 생겨도 신청 가능으로 바뀌지 않는지 확인한다.
- VoiceOver·TalkBack 및 최대 시스템 글자 크기 실기 확인은 사용자 요청에 따라 후순위로 둔다. P8 시험 운영 전에 기기·OS·재현 순서와 함께 검사한다.

일반 조회에는 추가 키 전달이 필요 없다. 다른 기관 연결 때 필요한 활용신청·계정은 해당 단계에서 확인한다. 현재 별도 가입이나 결제는 요구하지 않는다.
