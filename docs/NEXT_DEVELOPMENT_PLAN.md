기준 코드: e45ec79. 이 문서는 다음 작업의 제안 순서이며 기능 구현 완료나 배포 일정을 뜻하지 않는다.

[프로그램 명세서](PROGRAM_SPECIFICATION.md)는 목표 범위, [소스 명세서](SOURCE_SPECIFICATION.md)는 현재 구현을 설명한다.

## 1. 현재 위치

- LH 임대주택 목록·공급정보의 실제 연결과 상세 표시가 동작한다.
- 서울번동3 정정공고 한 건은 PDF·정정 관계가 검토 기록과 일치할 때 17항목을 제공한다.
- 다른 PDF·변경 문서는 재검토가 필요하다. 전체 신청 자격·별도 변경 공지·최종 유효성 검증이 남아 있다.
- 확인 완료 공고 생성은 차단되어 있다. 로그인·관심 공고 저장·맞춤 검색·경기 및 타 기관 연결도 아직 없다.

**바로 다음 작업은 P1의 검토 기록 검증·추출 절차 정리다.** 기존 안전장치를 유지하면서 다른 공고로 확대할 수 있는 기반부터 만든다. 로그인이나 기관 확대보다 먼저 정보 정확성의 기준을 정립한다.

## 3. 바로 착수할 P1 작업 명세

### 문제

현재 검토 기록은 한 공고의 JSON이며, 서버는 파일 해시와 관계를 대조한다. 기록 작성 시 필수 근거·페이지 범위·숫자 환산 검증을 수행하는 독립 도구는 없다. 런타임 결과 검증만으로 검토 내용 자체의 정확성까지 증명할 수 없다.

### 제안 작업

1. **검토 기록 전용 Schema 정의:** 공고 식별자, 파일 해시, 전체 페이지 수, 검토 시점·방법, 원공고/현재공고 관계, 사실별 페이지와 최소 근거, 미검토 범위를 필수화한다.
2. **검사 CLI 작성:** 공식 PDF와 기록을 입력받아 해시, 필수 항목, 페이지 범위, 중복 식별자, 불명확한 단위·조건을 검사한다. 파일을 읽는 도구이며 외부로 문서를 전송하지 않는다.
3. **추출 후보와 검토값 분리:** 텍스트/PDF 표 추출은 후보 단계로 보관한다. 렌더링 대조 전 값을 앱의 확인값으로 사용하지 않는다. 추출 실패·OCR 불확실성은 명시한다.
4. **기존 기록 이관:** 서울번동3 17항목을 새 형식으로 옮기고, 기존 화면·금액·단위·페이지 근거를 보존한다.
5. **검토 시점 표시:** 원문 재조회 시각과 항목 검토일을 구분해 응답과 화면에 표시한다.

예상 변경 위치(아직 생성하지 않은 파일 포함): `shared/contracts/` 검토 기록 Schema, `backend/document_reviews/`, 검토 도구 모듈, `lh_document.py`, `validation.py`, `useSearchApi.ts`, `LiveNotice.tsx`, 해당 테스트와 안내 문서.

### 수용 기준

- 정상 기록은 통과하고 공고 ID·해시·페이지 범위·근거가 잘못된 기록은 거부한다.
- 원격 PDF 바이트가 바뀌거나 정정 관계가 바뀌면 검토값을 보류한다.
- 보증금 천원→원 환산과 기본/최대 전환 조건, 소득 유무별 조건이 유지된다.
- 미검토 부분과 검토 날짜를 화면에서 구분할 수 있다.
- 문서 검토 기록 강화만으로 verified 생성 차단을 해제하지 않는다.

## 4. P2~P4에서 반드시 해결할 항목

| 항목 | 현재 한계 | 구현·검사 방향 |
|---|---|---|
| 표본 범위 | 마감 정정공고 한 건 | 공식 신규·정정·취소 표본 추가. 접수 중 표본이 없으면 합성 경계 검사와 실제 마감 자료를 구분 |
| 첨부 선택 | 공고문 PDF 한 개만 허용 | 파일 역할과 버전 구분. 복수 PDF는 임의 선택하지 않고 사유 표시 |
| 접수 회차 | 읽기용 일정 문장 | 시작/종료·시간대·신청 대상·신청 단계 구조화. 미명시 시각을 채우지 않음 |
| 금액 | 설명 문자열과 API fact가 별도 | 원문 단위·환산값·대상·전환 조건·유효 시점 보존, 공통 모집 단위에 연결 |
| 자격 | 공급 대상 개요만 제공 | 무주택 대상 범위·소득/자산 기준·가산·예외를 근거와 연결. 개인 적격 단정 금지 |
| 정정 | 상세 메타정보와 등록 기록 대조 | 별도 수정 공지·취소·일정 변경 조사. 관계 미해결 시 승격 금지 |
| 검증 완료 | verified 전면 차단 | 필수 항목별 검증 결과와 누락 이유 모델을 먼저 정의한 후 실제 판정기 연결 |

P4 완료는 화면에 확인 완료 탭이 있다는 것으로 판단하지 않는다. 한 항목이라도 핵심 근거가 누락·상충하면 실패하는 부정 사례 검사가 필요하다. 한 출처의 실패가 다른 공고의 유효한 근거를 지우지 않도록 출처 상태와 공고 상태를 분리한다.

## 5. 사용자가 직접 할 수 있는 확인

- 서버 재시작 → 새 검색 → 정정공고 상세 → 공급정보 조회 → 공고문 항목 확인을 실행한다.
- PDF 2쪽에서 21A 소득 유무별 기본 금액과 최대 전환 금액을 비교한다. 12쪽에서 접수와 서류제출 단계를 구분한다.
- 현재 공고가 마감으로 제외되고, 확인 항목이 생겨도 신청 가능으로 바뀌지 않는지 확인한다.
- iPhone VoiceOver / Android TalkBack에서 버튼·진행 안내·페이지 근거·목록 복귀를 확인하고 기기·OS·재현 순서를 기록한다.
- 최대 시스템 글자 크기에서 잘림·가로 넘침·버튼 접근 불가가 있는지 확인한다.

일반 조회에는 추가 키 전달이 필요 없다. 다른 기관 연결 때 필요한 활용신청·계정은 해당 단계에서 확인한다. 현재 별도 가입이나 결제는 요구하지 않는다.

## 6. 검증 및 인계 규칙

현재 기준 결과는 서버 131개, 참조 규칙 26개, 웹 접근성 41개 상태와 동작 검사 22개 통과다. [최근 기록](validation/2026-09-22_DOCUMENT_INTEGRATION.md)을 기준으로 변경한 경로와 의미 있는 실패 사례를 검사한다. 실기 미실행을 자동검사 통과로 대체하지 않는다.

각 작업 종료 시 다음을 남긴다.

- 변경 기능과 지원 공고·유형·기관 범위.
- 공식 근거와 실제 응답 / 합성 자료의 구분.
- 소스·데이터 계약·프로그램 명세의 변경 내용.
- 실행한 검사와 실패·미실행 항목.
- 다음 단계의 선행 조건 및 사용자가 확인할 사항.

공개 배포·로그인 제공자·운영 비용·시험 기기는 미확정이다. 구체 일정은 추가 표본과 접근 조건을 확인한 뒤 정한다. 새로운 외부 가입·유료 사용·공개 배포는 이 문서 작성만으로 수행하지 않는다.
