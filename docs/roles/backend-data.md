# 서버·데이터 전문가 지침

## 역할과 작업 계약
- 목표: 도시 검색 요청마다 공식 출처를 새로 조사하고, 검증에 필요한 근거와 진행 상태를 모바일 앱에 전달한다.
- 공통 입력: `../PROJECT_BRIEF.md`, `../PROJECT_INSTRUCTIONS.md`, 총괄이 승인한 데이터 계약, 조사·검증 역할의 출처 목록과 검증 기준.
- 담당 범위: 조사 작업 관리, 공식 출처별 수집 연결부, 데이터 정규화, 인증과 사용자별 저장, 장애 처리, 데이터 보존·삭제.
- 범위 밖: 모집 자격·공고의 법적 의미를 독자적으로 확정하지 않는다. 화면 읽기 동작은 모바일·접근성 역할과 공동 검증한다. 공식 연동 방법이나 API 제공 여부는 실제 문서와 응답을 확인하기 전 확정하지 않는다.
- 결과물: 구조·데이터 계약, 수집 연결부 명세, 작업 상태 전이, 접근 권한 규칙, 오류·재시도 정책, 검증 결과와 미확정 사항.

## 기술 기본안
Python·FastAPI를 조사 서버, Supabase를 계정·데이터 저장의 기본안으로 사용한다. 실제 지원 기능, 버전, 요금, 호스팅 제약, 장시간 작업의 실행 방식을 구현 착수 시 공식 문서로 확인한다. 작업 큐 제품과 배포 환경은 시험 운영 규모 및 접근 가능한 출처를 검증한 뒤 선택한다. 모바일 HTTP 연결 하나에 전체 조사 수명을 의존하지 않도록 서버 작업과 결과 조회를 분리한다.

## 검색과 병렬 조사
1. 서울·경기·인천 내 입력 지역을 정규화한다. 같은 이름의 지역이나 도시·구 경계가 모호하면 후보를 제시하고 잘못된 범위로 조사를 시작하지 않는다.
2. 검색 요청에 고유 작업 ID, 요청 시각, 지역 범위, 선택형 조건을 부여한다. 재전송된 동일 요청의 중복 실행을 제어한다.
3. 승인된 공식 출처 목록 중 해당 지역과 공공 임대·공공분양에 해당하는 출처를 선택한다. 민간 분양을 배제한다.
4. 독립된 출처 조사를 제한된 동시성으로 실행한다. 출처별 요청 제한, 서버 전체 동시 작업 상한, 시간 제한을 설정한다. 수치는 실제 부하·출처 제한을 근거로 확정한다.
5. 공고 목록뿐 아니라 원문·첨부파일·정정 및 취소 여부를 조사하고, 근거를 보존해 검증 단계로 전달한다.
6. 검증이 끝난 공고부터 부분 결과로 전달한다. 미완료 출처 수와 오류가 있는 출처를 함께 제공하여 부분 결과를 전체 조사 완료로 오해하지 않게 한다.
7. 사용자가 취소하면 신규 하위 작업을 시작하지 않고 실행 중 작업을 가능한 범위에서 중단한다. 취소 후 도착한 응답이 완료 상태를 덮어쓰지 않게 한다.
8. 완료·일부 완료·실패·취소를 구분하여 종료한다. 별도 정책 없이 무기한 재시도하지 않는다.

검색 때마다 신규 공식 출처 조사를 수행한다. 예약 일괄 수집이나 과거 저장 정보를 신규 조사 대신 사용하지 않는다. 기존 공고와 원문 기록은 중복 식별·변경 비교·관심 공고 참조에 사용할 수 있으나, 이번 조사에서 확인하지 않은 정보를 현재 확인된 결과로 내보내지 않는다. 출처가 제공하는 변경 없음 응답을 활용하더라도 해당 요청·응답과 확인 시각을 기록한다.

## 상태와 실패 계약
- 작업 상태: 대기, 조사 중, 검증 중, 완료, 일부 완료, 실패, 취소. 조사와 검증이 동시에 진행될 수 있으므로 출처별·공고별 상태도 별도로 관리한다.
- 시간: 서버 내부는 시간대가 있는 값으로 기록하고, 접수 일정의 해석·표시는 한국 시간 기준을 명시한다. 접수 회차나 대상자별 기간이 다르면 별도 구조로 보존한다.
- 임시 네트워크 오류와 요청 제한만 횟수·총시간 상한 내에서 지연을 늘려 재시도한다. 출처가 지정한 대기 시간을 존중한다.
- 접근 차단, 로그인 요구, 문서 해독 실패, 데이터 형식 변경, 영구 오류는 명시적으로 기록한다. 제한을 우회하거나 응답을 임의로 보충하지 않는다.
- ‘검색 결과 없음’은 계획된 출처의 조사가 정상 완료되고 현재 조건에 맞는 공고가 없을 때만 사용한다. 일부 출처 실패 시 ‘확인된 결과 없음, 일부 출처 확인 실패’처럼 구분한다.
- 진행 안내는 확인한 출처 수와 현재 단계 등 관측값을 사용한다. 근거 없는 완료율·남은 시간을 만들지 않는다.

## 최소 데이터 모델
- 검색 작업: 작업 ID, 지역, 시작·종료 시각, 상태, 취소 여부, 출처별 진행·오류, 조건 적용 여부.
- 공고: 내부 ID, 공식 출처 식별자, 기관, 제목, 주택 유형, 지역·주소, 원문 URL, 공식 공고 번호가 있을 경우 그 값.
- 모집 회차: 신청 대상 구분, 접수 시작·종료, 접수 예정·접수 중 등 판정과 판정 시각. 시각이 불명확하면 불확실성을 유지한다.
- 공고 버전: 최초·정정·취소 관계, 원문 확인 시각, 원문 식별값 또는 해시, 변경 이력. 기관 간 재게시를 구분하고 잘못 합치지 않는다.
- 추출 항목: 보증금·임대료·분양가, 면적, 공급 수, 자격 등. 각 항목에 값·단위·조건·근거 위치·검증 상태를 연결한다. 금액의 구간과 선택 조건을 단일 확정 금액으로 바꾸지 않는다.
- 근거: 출처 URL, 문서명, 페이지·표·문단 등 위치, 수집 시각, 원문 버전, 필요한 최소 발췌. 원문 보관 가능 범위와 기간은 확인하여 정한다.
- 사용자 저장: 사용자 ID에 속한 관심 공고와 선택적으로 저장한 맞춤 조건. 공고 삭제·마감 후에도 관심 항목을 현재 모집 중으로 표시하지 않는다.

## 검증 결과 전달
공식 근거를 확인한 상태와 신청 자격 판정은 다른 개념이다. 기본 목록에는 조사·검증 역할의 기준을 통과한 공고만 전달한다. 근거 부족이나 출처 충돌은 사유·영향 항목과 함께 ‘확인 필요’ 목록으로 분리한다. 선택형 맞춤 검색은 가능성 선별에만 사용하고 불명확한 자격을 적격·부적격으로 단정하지 않는다. 조건 값이 없으면 일반 조회가 가능해야 한다.

## 계정·개인정보
- 기본 조회와 저장하지 않는 맞춤 검색에는 로그인하지 않아도 되도록 설계한다. 관심 공고 및 맞춤 조건 저장은 인증 후 수행한다.
- 저장된 정보에는 사용자별 접근 제어를 적용하고 서버와 데이터베이스에서 검증한다. 화면에서 숨기는 것만으로 권한을 구현하지 않는다.
- 서비스용 비밀키와 수집 인증정보는 모바일 앱이나 응답에 포함하지 않는다.
- 생년월일·정확한 자산 금액 등 상세값 대신 실제 선별에 필요한 나이·소득·자산 구간을 우선 사용한다. 주민등록번호, 증빙서류, 불필요한 신원정보는 수집하지 않는다.
- 저장하지 않는 맞춤 조건은 응답 처리에 필요한 범위에서만 사용하고 작업 종료 후 삭제 정책을 적용한다. 일반 로그·분석 도구에 조건 원문을 기록하지 않는다.
- 조건 저장의 목적·항목·보존 기준을 사용자에게 알리고 직접 수정·삭제할 수 있게 한다. 계정 삭제 시 연관 저장정보 처리와 백업 만료 정책을 정의한다.
- 원문에 포함된 개인 명단 등은 앱 결과·로그에 불필요하게 복제하지 않는다. 외부 AI에 사용자 조건이나 개인정보를 전달하는 설계는 최소화하고 필요성과 처리 범위를 별도로 검토한다.

## 인계와 완료 기준
- 모바일 역할에 상태별 응답 예시, 오류 메시지용 코드, 재연결·취소·부분 결과 계약을 전달한다.
- 조사·검증 역할과 공고 버전·근거 위치·검증 상태를 합의한 뒤 구현한다. 문서 계약 변경은 총괄을 통해 버전을 올리고 관련 역할에 알린다.
- 실제 공식 출처 연결 검증, 한 출처 실패 중 다른 출처 결과 표시, 시간 초과 종료, 취소 후 상태 유지, 재시도 상한, 중복 요청을 확인한다.
- 사용자 A가 사용자 B의 관심 공고·조건을 읽거나 수정할 수 없는지 검증한다. 미로그인 조회와 미저장 조건이 불필요하게 영구 보관되지 않는지 확인한다.
- 공고 정정·취소·접수 마감·불명확한 일정·부분 출처 실패를 포함한 검수 결과와 남은 제약을 품질 검토자에게 제출한다. 성공 사례만으로 완료 처리하지 않는다.
